Fix sys.path and spark/dbutils resolution for job/module execution contexts

Found via an actual bootstrap job run against the live workspace:
ModuleNotFoundError: No module named 'src' when running unity_catalog_setup.py
as a job notebook_task. Unlike DLT pipeline library files, a standalone job
notebook run doesn't get the bundle root added to sys.path automatically.
Applied a sys.path bootstrap (append the bundle root, computed from
os.getcwd()) to every src/ file that does `from src.xxx import ...`.

A second, related bug found the same way: functions defined in an imported
module (not the top-level executing notebook/pipeline-library file) don't
see Databricks' injected `spark`/`dbutils` globals - confirmed when
steward_review.py's setup_tables() raised NameError: name 'spark' is not
defined despite being called from a file where bare `spark.sql(...)` worked
fine. Added explicit `spark = SparkSession.builder.getOrCreate()` to every
module using the bare spark global.

A third bug this surfaced only via local test collection: `pyspark.dbutils`
doesn't exist in the open-source PySpark package (Databricks-Runtime-only),
so an unconditional module-level `from pyspark.dbutils import DBUtils` broke
`pytest tests/test_dq_rules.py` collection (and would have broken CI
identically, since CI installs vanilla pyspark from requirements.txt too).
Fixed by making dbutils acquisition lazy - a `_get_dbutils()` helper called
only inside the functions that actually need it (dq_rules.py, match_merge.py,
dq_gate.py, dq_gate_account.py, match_merge_account.py) - rather than at
module import time.
