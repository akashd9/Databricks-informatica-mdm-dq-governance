# Pilot Validation Report

Generated by running `pilot/generate_pilot_dataset.py` (528 synthetic raw
records across 200 true customers, seeded for reproducibility) through
`pilot/run_pilot_validation.py` — a pandas reimplementation of the local DQ
and match/merge fallback logic (`src/quality/dq_rules.py`,
`src/mdm/match_merge.py`), used because those modules depend on a live
Spark/`dlt` context this environment doesn't have (no Java/cluster
available). Both implementations are driven by the same
`config/dq_rules.yml` / `config/match_rules.yml`.

## DQ Gate

At the original `min_dq_score_for_gold: 0.85`:

| Metric | Value |
|---|---|
| Mean DQ score | 0.953 |
| Quarantine rate | 4.4% (23/528) |

Well under the 15% threshold `src/observability/anomaly_gate.py` halts on.
**No change made** — the default was already reasonable against this pilot's
error rate (records were corrupted with a ~15% independent chance per
field, by construction in the generator).

## MDM Match/Merge Gate — Threshold Sweep

Pairwise precision/recall against the known ground truth
(`pilot/ground_truth.csv`, which `generate_pilot_dataset.py` writes since it
controls which records are true duplicates):

| `match_threshold` | precision | recall | f1 | golden records |
|---|---|---|---|---|
| 0.82 (original) | 1.000 | 0.603 | 0.752 | 298 |
| 0.75 | 1.000 | 0.871 | 0.931 | 231 |
| 0.70 | 1.000 | 0.975 | 0.987 | 205 |
| **0.65 (chosen)** | **1.000** | **1.000** | **1.000** | 197 |
| 0.60 – 0.45 | 1.000 | 1.000 | 1.000 | 197 |

**Finding:** 0.82 was badly under-matching — 40% of true duplicates never
got merged — while precision stayed perfect (1.000) across the *entire*
range tested, including thresholds as low as 0.45. That means, for this
pilot's data, there was no false-positive risk being traded away by lowering
the threshold; the original value was just leaving recall on the table.

**Change made:** `match_threshold` lowered from `0.82` to `0.65` in
`config/match_rules.yml` — chosen with margin below the 0.70 break-even
point rather than pushed to the theoretical floor, since synthetic data's
error patterns won't exactly match production's once real Informatica-scored
data is used.

**Caveat:** golden record count (197) came in slightly under the 200 true
customers, without any precision loss. Root cause: the synthetic name pool
is small (20 first names × 20 last names = 400 combinations for 200 draws),
so a handful of *distinct* synthetic customers coincidentally share an
identical name — a synthetic-data artifact, not evidence the matching logic
mismerges people. Real names won't have this collision rate.

## `auto_merge_threshold` — found unused, now wired in

`config/match_rules.yml` declared `auto_merge_threshold: 0.93` but no code
anywhere read it — dead config. Since it's exactly the "flag low-confidence
merges for human review" boundary the Phase 3 steward workflow needs, wired
it into `src/mdm/survivorship.py::build_golden_records` instead of deleting
it: every golden record now gets a `review_status` column —
`single_source` (no merge happened), `auto_merged` (confidence ≥
`auto_merge_threshold`), or `needs_review` (merged, but below it). Exposed
on `gold_customer_golden` for the steward review queue (Phase 3a) to consume
directly.

## Known limitation this pilot does NOT surface

This harness's `customer_id` values are source-prefixed (`ERP-0001`,
`CRM-0001`, ...) by construction in `generate_pilot_dataset.py`, so they're
guaranteed globally unique. The production code
(`src/mdm/match_merge.py`, `src/mdm/survivorship.py`) uses each source's raw
ID as-is with no such prefix — real ERP/CRM systems can independently assign
colliding IDs (ERP customer 1001 and CRM account 1001 being different
people). That's a real gap this pilot's clean synthetic IDs can't expose.

**Not fixed as part of this pilot** — it's a cross-cutting change to the
match/merge and survivorship join keys, out of scope for a threshold-tuning
pass. **Recommended before pointing this pipeline at real source data**: add
a globally-unique key (e.g. `concat(_source_system, ':', customer_id)`) as
the actual match/merge and survivorship join key, keeping raw `customer_id`
as a separate business-key attribute on the record.

## How to reproduce

```
python pilot/generate_pilot_dataset.py
python pilot/run_pilot_validation.py
```

Both scripts only need `pandas`, `pyarrow`, `jellyfish`, and `pyyaml` — no
Spark, no Java, no Databricks cluster.
